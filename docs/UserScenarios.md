# Orbit 사용자 시나리오

## 시나리오 1: 열린 탭을 작업 세션으로 저장

**전제:** 사용자가 Chrome에서 한 가지 이상의 작업을 수행하며 여러 탭을 열어두었다.

1. 사용자가 Orbit 사이드패널을 연다.
2. Orbit이 현재 창의 저장 가능한 탭을 보여준다.
3. 사용자가 저장을 실행한다.
4. Orbit이 탭을 작업 흐름별로 분류하고 임시 세션을 생성한다.
5. 백그라운드 요약이 완료되면 제목과 요약이 갱신된다.
6. 실패하면 실패 상태와 재시도 동작을 제공한다.

**완료 기준:** 선택한 모든 탭이 정확히 한 세션에 포함되고, 실패가 성공처럼 표시되지 않는다.

## 시나리오 2: 자연어로 과거 세션 검색

1. 사용자가 “지난주에 보던 일본 항공권 자료”처럼 목적 중심 검색어를 입력한다.
2. Backend가 검색어를 임베딩하고 관련 세션을 조회한다.
3. 설정에 따라 검색 결과를 리랭킹한다.
4. Extension이 관련 세션과 검색 상태를 표시한다.

**예외 흐름:** 검색 서비스 일부가 실패하면 품질 저하 상태를 표시한다. Backend 연결 자체가 실패하면 검색 결과 없음과 구분되는 오류를 보여준다.

## 시나리오 3: 세션 복원

1. 사용자가 세션 카드나 상세 화면에서 복원을 선택한다.
2. Orbit이 세션에 포함된 탭을 Chrome에 연다.
3. 일부 탭이 실패하면 성공한 탭과 실패한 탭 수를 구분해 알린다.

**완료 기준:** 실패한 탭 때문에 나머지 복원이 중단되지 않고 결과가 정확히 표시된다.

## 시나리오 4: AI 요약 재시도

1. 외부 AI 오류로 세션의 요약 상태가 `failed`가 된다.
2. 사용자가 재시도를 선택한다.
3. 상태가 `pending`으로 바뀌고 완료 여부를 폴링한다.
4. 성공하면 목록과 상세 화면이 모두 갱신된다.

## 시나리오 5: 민감 페이지가 포함된 세션 저장

1. 사용자가 금융, 정부, 의료 또는 로그인 페이지를 열어둔다.
2. 민감 도메인 제외 설정이 활성화되어 있다.
3. Orbit은 탭 제목과 URL은 복원을 위해 유지하되 본문과 발췌문은 전송하지 않는다.
4. 나머지 탭의 정보로 세션을 분류하고 요약한다.

## 시나리오 6: 빈 상태와 장애

- 저장된 세션이 없으면 Extension 설치 및 첫 저장 방법을 안내한다.
- 검색 결과가 없으면 쿼리와 일치하는 세션이 없음을 안내한다.
- Backend가 꺼져 있으면 서버 연결 오류를 안내한다.
- 외부 AI만 실패하면 저장된 임시 세션과 재시도 수단을 유지한다.

## 시나리오 7: 상시 수집 활성화 및 자동 세션 생성

**전제:** 사용자가 처음으로 Orbit의 상시 수집 기능을 사용하려 한다. 수집 기능은 기본적으로 꺼져 있다(opt-in).

1. 사용자가 설정의 "수집·동기화" 섹션에서 수집 마스터 토글을 켠다. 최초 활성화 시 안내 문구가 표시된다.
2. 사용자가 평소처럼 여러 사이트를 방문한다. Orbit은 방문마다 AI를 호출하지 않고, 방문 이벤트를 로컬 큐에 실시간으로 저장한다.
3. 자동 동기화 트리거(주기/개수/유휴) 또는 수동 "지금 저장"으로 쌓인 이벤트가 Backend로 전송된다.
4. Backend가 배치로 이벤트를 분석해 관련 있는 이벤트끼리 묶고, 기존 세션에 추가하거나 새 세션을 만든다.
5. 세션은 이후 방문·동기화가 반복될 때마다 자동으로 성장한다(사용자가 직접 만들지 않는다).

**완료 기준:** 수집을 켜지 않으면 이벤트가 쌓이지 않고, 켠 뒤에는 저장 버튼을 누르지 않아도 세션이 자동으로 생성·갱신된다.

**실패 처리:** 동기화가 실패하면 이벤트는 `pending` 상태로 남아 다음 동기화에서 재시도되며, 사용자에게 실패 상태가 표시된다. 수집 실패는 브라우징을 방해하지 않는다(fail-open).

## 시나리오 8: Timeline으로 탐색 경로 확인

1. 사용자가 사이드패널을 열면 기본 화면인 타임라인이 표시된다.
2. 오늘 방문한 페이지가 시각 역순으로, 각 항목에 할당된 세션 배지(또는 "분류 대기")와 함께 나열된다.
3. 사용자가 특정 세션 배지를 눌러 세션 상세로 이동한다.
4. 세션 상세의 "탐색 타임라인" 섹션에서 그 세션에 속한 방문들이 시간순으로 표시되어, 어떤 흐름으로 이 결론에 도달했는지 확인한다.
5. 필요하면 타임라인 항목을 클릭해 해당 페이지를 다시 연다.

**완료 기준:** 사용자가 탭 목록만으로는 알 수 없었던 방문 순서와 경로를 Timeline에서 재구성할 수 있다.

**예외 흐름:** 아직 동기화되지 않은 이벤트는 로컬 큐에서 바로 표시되며 "분류 대기"로 구분된다.

## 시나리오 9: Intent 검색("일본 여행 준비했던 거")

1. 사용자가 "일본 여행 준비했던 거"처럼 목적 중심 문장을 검색창에 입력한다.
2. Backend가 세션 벡터 검색과 이벤트 매칭(제목/검색어/도메인)을 함께 수행한다.
3. Extension이 결과를 "세션"과 "관련 기록" 두 그룹으로 나눠 보여준다 — 세션 카드와 개별 방문 이벤트가 함께 표시된다.
4. 사용자가 세션이나 개별 이벤트를 선택해 복원하거나 페이지를 다시 연다.

**완료 기준:** 세션에 아직 할당되지 않은 방문 기록도 제목/검색어/도메인 매칭을 통해 관련 기록으로 노출된다.

**예외 흐름:** 검색 서비스 일부가 실패하면 품질 저하 상태를 표시한다(시나리오 2 정책 승계). Backend 연결 자체가 실패하면 검색 결과 없음과 구분되는 오류를 보여준다.

## 시나리오 10: 동기화 전 이벤트 삭제

1. 사용자가 타임라인에서 아직 동기화되지 않은 방문 이벤트를 확인한다.
2. 보이고 싶지 않은 이벤트를 선택해 삭제한다.
3. Orbit은 해당 이벤트를 로컬 큐에서 즉시 제거하고 이후 동기화 대상에서 제외한다.
4. 이미 동기화되어 서버에 저장된 이벤트는 별도로 삭제를 요청하면 서버에서도 제거되고, 연결된 세션 정보(session_events)도 함께 정리된다.

**완료 기준:** 사용자가 원치 않는 방문 기록을 동기화 이전(로컬)과 이후(서버) 어느 시점에서도 통제할 수 있다.

**실패 처리:** 삭제 요청이 실패하면 이벤트는 그대로 남고 실패 상태가 표시된다(성공으로 오인되지 않는다).

## 시나리오 11: 자연어로 열린 탭 찾아 이동

1. 사용자가 새 탭 또는 사이드패널 Ask AI에 “아까 보던 영상으로 돌아가자”라고 입력한다.
2. Orbit은 통합 Ask 의도 라우터로 이동 요청인지 판별한다. 정확한 제목·URL 일치는 로컬에서 처리한다.
3. 간접 이동 표현이면 모든 일반 Chrome 창의 탭 제목·호스트·URL path를 backend에 보내
   이동 의도와 후보 의미 유사도를 query/passage 임베딩으로 계산한다.
4. 의도와 후보 점수·격차가 안전 기준을 모두 통과하면 응답 탭 ID를 현재 목록에서 재검증하고,
   해당 창을 앞으로 가져와 탭을 활성화한다.
5. 이동 결과와 복수 일치 여부를 Ask AI 답변 목록에 남긴다.

**예외 흐름:** 일치 점수가 낮거나 상위 후보가 비슷하면 구체적인 제목이나 사이트를 요청한다.
실행 직전 탭이 닫혔으면 별도로 알린다. resolver가 비이동 질문으로 판단하거나 장애가 나면 기존 Ask AI
스트리밍 경로를 유지한다. 후보 제목·URL과 벡터는 DB·Qdrant에 저장하지 않는다.

상위 후보 점수는 충분하지만 두 개 이상이 비슷하면 자동 이동하지 않고 Ask 답변 안에 최대 3개를
제목·호스트/경로와 함께 표시한다. 사용자가 후보를 클릭하면 현재 열린 탭 ID를 다시 검증한 뒤 이동한다.

## 시나리오 12: 열린 탭을 Chrome 북마크에 추가

1. 사용자가 세션 화면의 ‘열린 탭 찾기·북마크’를 펼친다.
2. 제목이나 URL로 탭을 필터링하고 북마크할 탭을 선택한다.
3. `북마크 N` 버튼을 누르면 Chrome 기본 ‘기타 북마크’에 추가된다.
4. 이미 북마크된 URL과 선택 내 중복 URL은 건너뛰고 처리 결과를 알린다.

**완료 기준:** 사용자가 명시적으로 선택한 bookmark 가능한 탭만 생성되며, 일부 실패가 나머지 생성을 막지 않는다.

## 시나리오 13: Ask AI가 세션 찾기와 내용 질문을 구분

1. 사용자가 “리액트 공부했던 세션 찾아줘”라고 입력하면 `find_sessions`로 판별한다.
2. Backend는 관련 세션을 최대 5개 반환하고 별도 답변 생성 없이 목록 확인을 안내한다.
3. 사용자가 “리액트 세션에서 Zustand 장점이 뭐였지?”라고 입력하면 `search_session`으로 판별한다.
4. 가장 가까운 세션 1개의 이벤트 중 질문과 의미가 가까운 페이지를 골라 스트리밍 답변을 만든다.
5. “전에 공부한 상태관리 내용을 정리해줘”처럼 세션 자체가 아닌 사실을 묻는 질문은
   `search_memory`로 판별해 관련 세션 최대 3개에서 근거를 찾는다.

**완료 기준:** 세션 자체를 찾는 요청에는 세션 목록이, 저장된 사실을 묻는 요청에는 질문 관련 페이지를
근거로 한 답변이 표시된다. 의도가 모호하면 전체 기록 검색으로 fallback하며 탭을 자동 실행하지 않는다.

**예외 흐름:** 이벤트 임베딩이 실패하면 기존 relevance·체류 시간 기반 페이지 선택을 사용한다.
통합 라우터가 실패하면 전체 기록 검색으로 이어져 질문 자체가 유실되지 않는다.
