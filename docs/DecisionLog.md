## 2026-08-12 — 타임라인은 "방문 기록 대체"로 확정하고 상단 카드를 표면에 흡수시킨다

- 상태: 승인
- 배경: 타임라인 상단에 `SyncStatusCard`(수집 상태 + 오늘 방문/미처리/마지막 동기화 + 지금 저장)가,
  하단에 `이번 주 탐색 분석` 카드가 상시로 붙어 있었다. 두 카드가 세로 약 160px를 먹어
  목록이 5~6줄 밀렸다. 조사 중 목록의 원천이 서버가 아니라 로컬 큐(48시간 보관)라는 것과,
  분석 카드만 7일치를 보고 있어 한 화면 안에서 시간 범위가 어긋나 있다는 것을 확인했다.
- 결정:
  - 타임라인의 역할을 **브라우저 방문 기록의 대체**로 확정한다. 최근 48시간을 훑고 즉시
    재진입하는 화면이며, 오래된 기록은 세션 탭과 Ask가 맡는다.
  - `이번 주 탐색 분석` 카드를 제거한다.
  - `SyncStatusCard`를 해체해 세 기능을 각각 기존 표면에 흡수시킨다.
    - 지금 저장 → 상단 바 새로고침 아이콘에 통합(동기화 요청 + 쿼리 무효화)
    - 미처리·마지막 동기화 → sticky 날짜 헤더 우측(맨 위 그룹에만)
    - 수집 opt-in 안내 → 조건부. 기록 없으면 전체 화면, 있으면 한 줄, 켜져 있으면 없음
  - 로컬 필터 입력을 추가한다.
  - 연속된 같은 도메인 방문 뭉치기는 이번에 하지 않는다.
- 대안:
  - 상태 카드를 얇은 스트립으로 축소 → 여전히 상시 행 하나를 소비한다. 날짜 헤더가 어차피
    sticky라 그 자리를 겸하면 추가 비용이 0이다.
  - 지금 저장을 타임라인 헤더에 따로 두기 → 사용자가 새로고침 아이콘에 기대하는 동작과
    중복된다. 버튼 두 개가 사실상 같은 의도를 가진다.
  - 검색을 Ask에만 맡기기 → Ask는 서버 데이터만 본다. 방금 본 페이지는 아직 로컬 큐에
    `분류 대기`로 있어 검색 사각지대가 된다. "5분 전에 본 것"이 가장 자주 찾는 대상이라
    치명적이다.
- 근거와 영향:
  - 상단 카드 제거로 첫 화면 목록 노출이 5~6줄 늘어난다.
  - 동기화 상태는 정상일 때 시각만, 문제일 때 점+개수로 나타난다. 상시 3열 숫자판보다
    신호 대 잡음이 낫다.
  - 필터는 로컬 배열 연산이라 네트워크를 타지 않고 즉시 반응하며, Ask(의미 검색·과거)와
    역할이 겹치지 않는다.
  - 타임라인을 전체 기록 열람으로 넓히려면 백엔드에 기간 조회를 새로 열어야 한다. 미결정으로
    남긴다.

## 2026-08-12 — 사이드패널에서 수동 세션 저장을 없애고 Ask AI를 상시 독으로 내린다

- 상태: 승인
- 배경: 세션 탭 상단에 `현재 세션` 카드가 있어 "지금 열린 탭을 세션으로 저장" 버튼을 제공했다.
  세션화는 이미 이벤트 배치가 담당하므로 이 버튼은 같은 결과를 다른 경로로 한 번 더 만드는
  중복 입구였다. 한편 Ask AI는 상단 세그먼트 탭 3개 중 하나를 차지해, 다른 탭을 보는 도중에
  질문하려면 탭을 옮겨야 했다.
- 결정:
  - `현재 세션` 카드와 수동 저장 경로(`useSaveSessionsClustered`, 클러스터링 진행 표시)를 UI에서 제거한다.
  - Ask AI를 탭에서 빼고 메인 탭(타임라인/세션/열린 탭) 하단에 상주하는 입력창으로 내린다.
    질문을 보내면 답변 화면이 그 위로 올라오고, 상단 바가 `‹ Ask AI` 헤더로 바뀐다.
  - 비워진 세 번째 탭에 기존 `열린 탭 찾기·북마크`를 올린다.
  - 세션 목록은 카드 그리드에서 행 리스트로 바꾸고, 요약·탭 목록·복원·삭제는 caret 펼침 안에 둔다.
- 대안:
  - Ask AI 탭 유지 + 하단 독 추가 → 같은 기능의 입구가 둘이 되어 탭 자리만 낭비한다.
  - 행 hover 시 복원 버튼 노출 → 사이드패널 폭에서 파비콘 스택과 자리가 겹친다.
  - 복원·삭제를 상세 뷰로만 밀기 → 자주 쓰는 복원이 2단계가 된다.
- 근거와 영향:
  - 검색 경로는 원래부터 Ask 하나뿐이었다(`useAskConversation` 이 `search_memory` /
    `search_session` / `navigate_tab` 으로 라우팅). 채팅창으로 내려도 잃는 검색 기능이 없다.
  - 대화 턴은 모듈 전역 store 에 있어 탭을 옮겨도 유지된다. 답변 화면은 언마운트하지 않고
    transform 으로만 오르내려 스크롤 위치를 지킨다.
  - 하단 독이 세로 약 60px 을 상시 점유하고 행 높이도 커져, 한 화면에 보이는 세션 수가 줄어든다.
  - `lib/api.ts` 의 `saveSessionsClustered` 와 백엔드 `/sessions/cluster` 는 남겨 둔다.
    API 경계까지 함께 지우는 것은 이번 UI 변경의 범위를 넘는다.

## 2026-08-12 — 세션 이름 수정은 title 을 덮지 않고 별칭(alias)에 저장한다

- 상태: 승인
- 배경: `PATCH /sessions/{id}` 가 `session.title` 을 덮어쓰고 있었다. 그런데 `title` 은
  사용자에게 보여 주는 라벨이자 동시에 내부 계산의 입력이다.

  | 위치 | 용도 | 이름이 바뀌면 |
  | --- | --- | --- |
  | `api/sessions.py` `_embed_and_upsert` | Qdrant 임베딩 텍스트 | 저장된 벡터가 옛 제목 기준이라 검색이 어긋난다 |
  | `services/merge_service.py` `_title_jaccard` | 병합 게이팅 | 병합 판정이 사용자 작명에 좌우된다 |
  | `services/merge_suggester.py` | 후보 토큰 겹침 | 위와 같음 |
  | `services/session_updater.py` | 배치가 제목을 다시 만든다 | **사용자가 바꾼 이름이 덮인다** |
  | `services/recommender/service.py` | 추천 신호 term 추출 | 추천 근거가 흔들린다 |

- 결정:
  - `sessions.alias VARCHAR(100)` 을 추가한다(additive). 사용자 편집은 **오직 alias** 만 바꾼다.
  - `PATCH /sessions/{id}` 의 본문을 `{"title": ...}` 에서 `{"alias": ...}` 로 바꾼다.
    `null` 또는 공백만 있는 문자열은 별칭 지우기로 본다.
  - **표시 이름은 서버가 응답 경계에서 합친다.** `SessionDetail.title` 은
    `coalesce(alias, title)` 이고, 원본 `title` 은 응답에 싣지 않는다.
    `alias` 는 편집창 초기값·되돌리기 판단용으로 따로 내려보낸다.
  - 컬럼만 뽑는 조회(타임라인·검색의 `session_title`)는 SQL 식 `SESSION_DISPLAY_TITLE` 을 쓴다.
  - 병합 제안은 점수용 `title` 과 표시용 `display_title` 을 `SessionMeta` 안에서 분리한다.
- 대안:
  - **클라이언트가 합친다**: 화면이 여러 개(대시보드 캔버스·네비게이터·트레이·상세·사이드패널·
    검색·추천)라 한 곳만 빠져도 같은 세션이 두 이름으로 보인다. 경계 한 곳에서 끝내는 편이 안전하다.
  - **title 을 그대로 바꾸고 원본을 별도 컬럼에 백업**: 배치 세션화가 다시 덮어쓰는 문제가 남는다.
- 근거와 영향:
  - 사용자에게는 그냥 "이름 수정"으로 보이고, 내부 계산은 AI 가 만든 이름을 계속 기준으로 쓴다.
  - **의도적 예외** — Ask 프롬프트(`ask_service._session_block`)와 추천 리랭크 프롬프트는
    `SessionDetail`/`SessionSignals` 를 거치므로 별칭을 본다. 사용자가 부르는 이름이 질의와
    더 가까우므로 그대로 둔다. 저장된 벡터와 대조하는 경로가 아니라 안전하다.
  - 예전 rename 으로 이미 `title` 이 바뀐 기존 세션은 마이그레이션하지 않는다 — 되돌릴 원본이 없다.

## 2026-08-12 — 네비게이터 세션 정렬은 표시 이름 기준으로 한다

- 상태: 승인
- 배경: 네비게이터에 정렬이 없어 목록이 항상 최신순 하나뿐이었다.
- 결정: `sortSessions(sessions, 'recent' | 'title')` 순수 함수. `recent` 는
  `buildAtlasSessions` 가 만들어 둔 마지막 활동 시각 내림차순을 유지하고, `title` 은
  `localeCompare(_, 'ko', { numeric: true })` 로 정렬한다. 폴더 자체 순서는 사용자가 만든
  `position` 을 유지한다. 상태는 `nav-state` 에 둬 메인·아틀라스가 공유한다.
- 근거와 영향:
  - **표시 이름(별칭 반영) 기준**으로 정렬한다. 사용자가 별칭을 붙였는데 원래 이름으로
    정렬되면 가나다순 목록이 뒤죽박죽으로 보인다.
  - `numeric: true` — "실험 10" 이 "실험 2" 앞에 오는 사전순 결과를 피한다.

## 2026-08-12 — 궤도 위 점 배치는 고정 슬롯이 아니라 선택 기준 연속 각도로 한다

- 상태: 승인 (2026-08-07 "궤도 정원과 회전" 결정을 대체)
- 배경: 앞면 반원을 7개 고정 슬롯으로 나눠 점을 넣는 모델에서는 선택된 페이지가 어느
  슬롯이든 갈 수 있었다. 칩이 있는 궤도는 최하단을 칩 자리로 비우려고 점을 좌우로 갈라
  놓아, 선택된 페이지가 화면 끝에 붙는 일이 생겼다(사용자 첨부 이미지). 뒤편 점은 잘라내
  흔적을 남기지 않아 "궤도 밖에 더 있다"가 숫자로만 표현됐다.
- 결정:
  - **선택된 페이지는 언제나 궤도 최하단(90도), 중심 노드 바로 아래**에 놓는다.
    회전량이 곧 "지금 최하단에 있는 점의 인덱스"이며, 선택과 회전은 같은 것이다.
  - 최하단 기준 좌우 3칸(`ORBIT_VISIBLE_SIDE`)은 균등 간격으로 온전히 그린다.
    그 바깥 3칸(`ORBIT_EDGE_HINTS`)은 간격을 0.34배로 눌러 양 끝에 몰아 두고,
    크기·농도를 0 으로 수렴시켜 **"밖에 더 있다"는 신호**로 쓴다. 더 먼 점은 그리지 않는다.
  - 점이 7개 이하면 간격을 벌려 전부 온전히 보이고 축소 점이 없다.
  - 좌우 이동은 항상 **최단 방향**으로 돈다(`alignOffset`). 마지막에서 첫 페이지로 넘어가도
    한 칸만 돈다.
  - 키 배정: `←→` = 페이지 이동, `↑↓` = 세션(궤도) 이동. 선택이 회전을 끌고 오므로
    "회전 전용 키"는 두지 않는다.
- 대안:
  - 슬롯 모델 유지 + 선택 슬롯만 강조: 선택이 어디 있는지 매번 눈으로 찾아야 한다.
  - 궤도를 완전한 타원으로 바꿔 아래 절반까지 사용: 슬롯이 두 배가 되지만 세션 칩·트레이와
    자리가 겹치고, "선택이 늘 같은 자리"라는 이번 요구는 여전히 풀리지 않는다. 보류.
- 근거와 영향:
  - 선택 위치가 고정되면 좌우 이동의 결과를 예측할 수 있고, 연결선이 늘 수직으로 서서
    어느 점이 선택됐는지 찾을 필요가 없다.
  - 회전을 **좌표가 아니라 각도로 보간**해야 한다. `left/top` 을 전이시키면 두 점을 잇는
    현을 따라가 궤도를 벗어난다. `requestAnimationFrame` 으로 회전량만 감쇠 보간하고
    좌표는 매 프레임 다시 계산한다.
  - `beyond` 를 정수 단계가 아닌 연속값으로 노출한다. 회전이 연속이라 온전한 점에서
    축소 점으로 끊김 없이 이어져야 한다.
  - 궤도 하나가 담는 점의 수에 상한이 사라진다. **`ORBIT_CAPACITY` 와
    `splitPagesIntoOrbits` 는 폐기했다**(2026-08-12 후속) — 세션 씬은 페이지가 몇 개든
    궤도 하나를 만든다. 정원을 남겨 두니 페이지 23개짜리 세션이 14+9 두 궤도로 쪼개져
    "세션 하나가 왜 둘로 보이느냐"는 문제가 됐다.

## 2026-08-07 — 세션 정리는 자동 클러스터링이 아니라 사용자 폴더로 한다

- 상태: 승인
- 배경: 대시보드의 세션 목록이 시간축 단일 정렬이라 기록이 쌓이면 스크롤로만 찾게 된다.
  주제 축을 하나 더 주는 2뎁스가 필요했다. `atlas/data.ts` 에는 "백엔드에 Orbit 엔티티가
  없어 세션을 중심 노드로 직접 쓴다"는 주석이 남아 있었고, 캔버스의 궤도는
  `PAGES_PER_ORBIT = 8` 로 페이지를 자르는 순수 페이지네이션이라 의미가 없었다.
- 결정:
  - 주제 그룹은 **사용자가 직접 만드는 폴더**로 한다. 자동 클러스터링을 쓰지 않는다.
  - 세션은 폴더 하나에만 속한다(단일 소속, `sessions.folder_id`).
  - 폴더는 백엔드에 저장한다(`folders` 테이블).
  - 캔버스 폴더 씬은 3계층 — 중심=폴더, 궤도 한 줄=세션, 그 궤도의 점=해당 세션의 페이지.
  - 궤도는 앞면 7개만 노출하고 나머지는 뒤편에 보관해 회전으로 접근한다.
- 대안:
  - 자동 임베딩 클러스터링 — 정리 노동이 0이지만 오분류가 필연이다. 2뎁스에서 오분류는
    "찾는 세션이 엉뚱한 서랍에 들어가 보이지 않는" 실패가 되어 재발견 도구에 치명적이다.

  - 확장 로컬 저장(chrome.storage) — 백엔드 변경이 없지만 기기가 바뀌면 정리가 사라지고,
    서버에서 세션이 병합·삭제되면 고아 참조가 생긴다.
  - 궤도 = 시간축, 점 = 세션 — 밀도 통제는 가장 좋지만 사용자가 원한 주제 축이 아니다.

## 2026-08-07 — 인증: 구글 로그인 전용 + 자체 JWT, 로그인 필수

- 상태: 승인
- 배경: 백엔드 API 6개가 전부 무인증으로 열려 있었고, `user_id` 컬럼은 있으나 전 구간
  `"local"` 로 하드코딩돼 있었다. 스키마는 멀티유저를 염두에 뒀지만 주체가 없었다.
- 결정:
  - 로그인 수단은 **구글 계정만**. 비밀번호를 저장하지 않는다.
  - 익스텐션은 `chrome.identity.getAuthToken` 으로 access token 을 받고,
    백엔드가 이를 1회 검증한 뒤 **자체 JWT(HS256)** 를 발급한다.
  - 사용자 매칭 기준은 이메일이 아니라 **구글 `sub`** — 이메일은 바뀔 수 있다.
  - **로그인 필수.** 비로그인 상태에서는 화면도 API 도 열지 않는다.
  - 인증 도입 전 쌓인 `user_id="local"` 데이터는 **최초 가입자 한 명에게만** 이관한다.
- 대안: (1) `launchWebAuthFlow` — 팝업과 토큰 교환을 직접 구현해야 함.
  (2) 구글 ID 토큰을 매 요청 검증 — 만료 주기를 우리가 못 정하고 검증 비용이 매 요청 발생.
  (3) 로그인 선택(로컬 모드 병행) — 두 모드를 모두 유지해야 하고 API 경계가 계속 열려 있음.
- 근거와 영향:
  - `getAuthToken` 은 access token 을 주므로 백엔드가 `tokeninfo` 로 **`aud` 가 우리
    client_id 와 일치하는지 반드시 확인**해야 한다. 이 검사가 빠지면 다른 앱용으로 발급된
    토큰으로도 우리 계정에 로그인할 수 있다(confused deputy). 이번 구현의 핵심 방어선이며
    전용 테스트(`test_verify_rejects_token_issued_to_another_client`)로 고정했다.
  - 인증 의존성은 **라우터 단위**로 걸었다(`main.py`). 엔드포인트마다 붙이면 언젠가
    하나를 빠뜨리고 그 경로로 데이터가 샌다.
  - 신규 의존성 `PyJWT`. JWT 를 직접 구현하면 alg 혼동·타이밍 공격 같은 함정이 있다.
  - 배포 시에는 HTTPS 와 프로덕션 도메인 `host_permissions` 가 추가로 필요하다.

## 2026-08-07 — 데이터 격리: 모든 조회를 소유자로 제한

- 상태: 승인
- 배경: 인증만 붙이면 "로그인은 되는데 남의 데이터가 보이는" 상태가 된다.
  실제로 `sessions.py` 는 `user_id` 필터가 **아예 없었다**.
- 결정: 조회·수정·삭제 전 구간에 소유자 조건을 넣는다.
  - 세션 단건 접근은 `_owned_session()` 을 거치고, 남의 세션은 **403이 아니라 404** 로 답한다
    (403은 "그 id의 세션이 존재한다"는 사실을 알려준다).
  - 벡터 검색 결과는 Qdrant 에 소유자 정보가 없으므로 **SQL 단계에서 반드시 거른다**.
  - 배치 파이프라인은 **한 배치에 한 사용자** 이벤트만 claim 한다. 시간 gap 그룹화가
    사용자 경계를 모르기 때문에 섞으면 서로 다른 사람의 방문이 한 세션으로 묶인다.
  - 후보 세션 검색·병합 제안·자동 병합도 같은 사용자 안에서만 수행한다.
- 근거와 영향: 26개 보호 경로 전부에 대해 토큰 없음/위조 토큰 두 경우를 실제 요청으로
  검증하는 테스트(`test_auth_boundary.py`, 56건)를 뒀다. 라우터를 새로 추가해도
  이 테스트가 자동으로 커버한다.

## 2026-08-07 — 추천 세션: 다중 신호 후보 + LLM 리랭킹, 협업 필터링 미도입

- 상태: 승인
- 배경: 추천을 최신순이나 단일 모델로 만들면 "방금 본 것"만 반복 노출된다. Orbit은
  다수 사용자 간 콘텐츠 추천이 아니라 **단일 사용자의 탐색 연속성**이 핵심이다.
- 결정: `후보 스코어링(규칙+임베딩) → 상위 10~20개 → LLM 리랭킹 → 3개` 구조.
  1차 점수 = `0.35*similarity + 0.30*unfinished + 0.15*recency + 0.10*revisit + 0.10*current_context`.
  최종 3개는 성격(continue / related / rediscover)을 섞고 각각 **추천 이유**를 붙인다.
  Bayesian·collaborative filtering은 초기 버전에서 쓰지 않는다.
- 대안: 최신순 정렬(맥락 무시), 임베딩 유사도 단독(미완료·반복 신호 소실),
  전 후보를 LLM에 투입(비용이 세션 수에 비례).
- 근거와 영향: 1차 점수는 DB·임베딩만 쓰므로 저렴하고, LLM은 추천 경로에서 한 번만 부른다.
  가중치와 신호 정의는 테스트로 고정했다(`test_recommender_scoring.py` 22건) —
  가중치를 바꾸면 테스트가 깨지도록 의도했다.
  LLM 응답은 신뢰하지 않는다: 인덱스 범위·중복·성격·이유 길이를 검증하고 어긋나면
  규칙 기반으로 폴백한다. 추천이 안 나오느니 덜 정교한 추천이 낫다.
  향후 implicit feedback(클릭·복원·무시·체류시간)이 쌓이면 개인별 weight 학습이나
  bandit으로 확장할 수 있도록 신호를 분리해 두었다.

## 2026-08-07 — 추천 갱신: 서버 캐시 + 지연 재계산 (stale-while-revalidate)

- 상태: 승인 (갱신 시점은 사용자가 "추천대로 구현"으로 위임)
- 배경: 새 탭은 하루에 수십 번 열린다. 열 때마다 LLM을 부르면 비용이 열람 횟수에
  비례하고 화면도 매번 로딩을 기다린다. 반대로 완전 고정이면 방금 탐색한 맥락이 빠진다.
- 결정: 추천 결과를 사용자별로 DB에 캐시(TTL 30분, `RECOMMENDATION_TTL_MINUTES`).
  새 탭을 열면 **캐시를 즉시 반환**하고, TTL이 지났으면 응답은 그대로 준 뒤
  **백그라운드에서 재계산**한다. 다음 새 탭부터 새 추천이 보인다.
  화면의 3개 캐러셀 회전은 이미 받은 결과를 돌리는 것이라 추가 호출이 없다.
  동기화 배치가 세션을 갱신하면 캐시를 낡은 것으로 표시한다(삭제가 아니라 `computed_at`
  을 과거로 미는 방식 — 다음 요청이 빈 화면을 거치지 않는다).
- 대안: 매 요청 계산(비용·지연), 고정 TTL 후 동기 재계산(그 요청만 느려짐),
  클라이언트 폴링(호출 증가).
- 근거와 영향: LLM 호출이 **사용자당 시간당 최대 2회**로 묶인다. 최초 요청만 동기
  계산하는데, 이는 빈 화면을 보여주지 않기 위한 의도적 예외다.
  캐시 정책은 테스트로 고정했다(`test_recommender_cache.py`) — 신선한 캐시인데
  재계산하면 실패한다.
