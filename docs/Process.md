# Orbit 작업 프로세스

이 문서는 `AGENTS.md`의 작업 규칙을 프로젝트에서 실행하기 위한 요약 절차다. 충돌 시 `AGENTS.md`를 우선한다.

## 1. 작업 시작

1. 요청 범위와 완료 조건을 확인한다.
2. `git status`로 기존 사용자 변경을 확인한다.
3. 관련 코드, 테스트, README와 설계 문서를 읽는다.
4. `docs/Plan.md`를 현재 작업에 맞게 갱신한다.
5. API, 데이터, 권한, 사용자 흐름 변경이면 구현 전에 사용자 결정을 받는다.

## 2. 구현

1. 여러 계층에 걸친 변경은 스키마와 타입 계약부터 정리한다.
2. 실패와 경계 조건을 재현하는 테스트를 먼저 추가하거나 함께 작성한다.
3. 계획에 적힌 최소 범위만 수정한다.
4. 외부 API는 서비스 계층 뒤에서 호출하고 타임아웃과 제한된 재시도를 적용한다.
5. loading, empty, success, error 상태를 각각 확인한다.

## 3. 검증

프로젝트가 제공하는 명령을 우선하며 가능한 범위에서 다음 순서로 실행한다.

1. 관련 Backend 테스트
2. 전체 Backend 테스트
3. Extension TypeScript 검사와 빌드
4. Frontend TypeScript 검사와 빌드
5. 통합 스모크 테스트
6. `git diff --check`

실행하지 못한 검증은 이유와 함께 기록한다.

## 4. 문서화

- 작업 계획과 실제 범위를 `Plan.md`에서 일치시킨다.
- 주요 결정은 `DecisionLog.md`에 기록한다.
- 조사 내용은 `Research.md`에 기록한다.
- 작업, 오류, 해결, 검증 결과는 `WorkLog.md`에 기록한다.
- 화면 흐름이나 API가 바뀌면 관련 설계 문서와 README도 갱신한다.

## 5. 완료 및 Git

1. `ReviewChecklist.md`로 자체 검토한다.
2. 변경 파일과 사용자 변경이 섞이지 않았는지 확인한다.
3. 큰 변경은 규칙에 맞는 작업 브랜치에서 수행한다.
4. 커밋, push, PR은 요청받은 범위에서만 수행한다.
5. 최종 보고에는 변경, 검증, 가정, 남은 위험을 포함한다.

## 6. UI · 디자인 변경 절차

디자인 개편처럼 화면 전체에 걸치는 변경은 파일을 흩뿌리기 쉬우므로 아래 순서를 따른다.
기준 계획은 `Plan.md`이며, 이 절차는 그 계획을 실행하는 방법이다.

### 6.1 기준 정하기

1. 디자인 원본(목업·시안)의 **토큰**을 먼저 표로 추출한다 — 색, 타이포, 반경, 그림자, 간격.
   개별 화면의 CSS를 베끼기 전에 토큰부터 확정해야 화면 간 일관성이 유지된다.
2. 원본이 쓰는 외부 의존(CDN 폰트·아이콘 스크립트 등)을 확인하고 MV3 CSP에서
   가능한 대체재를 정한다. 원격 리소스는 익스텐션에 반입하지 않는다.
3. 브랜드 에셋은 **배경이 없는 원본**을 쓴다. 단색 배경이 구워진 이미지는
   크롬 UI(사이드패널 헤더, 툴바)에서 주변과 분리돼 보인다.

### 6.2 적용 순서

토큰 → 부품 → 화면 순으로 내려간다. 반대로 하면 같은 값을 여러 번 고치게 된다.

1. 토큰 파일 한 곳(`tailwind.css`의 `@theme`, 또는 홈의 `:root`)을 교체한다.
2. 공용 부품(버튼·배지·카드·플레이스홀더)의 반경·그림자·상태색을 맞춘다.
3. 화면별 잔여 하드코딩 색상을 토큰으로 흡수한다.
4. 새 화면은 기존 화면의 스타일 파일과 **격리**한다. 엔트리포인트가 다르면
   CSS도 분리해 상호 오염을 막는다.

### 6.3 완성도 확인

1. loading · empty · error 상태도 새 팔레트로 확인한다. 정상 화면만 보고 끝내지 않는다.
2. `prefers-reduced-motion`에서 애니메이션이 멈추는지 확인한다.
3. 좁은 폭(사이드패널 320px 전후)과 넓은 폭(새 탭)을 모두 확인한다.
4. 시각 확인은 `pnpm build` 후 실제 크롬에 로드해서 한다. 빌드 산출물만으로는 판단하지 않는다.

### 6.4 목업 데이터 취급

시안의 더미 데이터를 임시로 옮겨 쓸 때는 다음을 지킨다.

1. 모듈명과 상단 주석에 목업 데이터임을 명시한다(`*-mock.ts`).
2. 실데이터 연결이 미완임을 `DecisionLog.md`에 한시적 조치로 기록한다.
3. 더미 데이터를 실제 도메인 타입과 섞지 않는다. 별도 타입으로 둔다.
