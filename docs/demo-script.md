> 개정: 2026-10-23 — 결선 시연 형식(클라우드 백엔드·노트북 2대)과 **제주 여행 준비** 시나리오로 바꿨다. 질문은 같은 날 일상 탐색 재생에서 확인한 문항으로 골랐다(§3).

## 1. 시연 범위와 판정 원칙

- 백엔드(FastAPI·PostgreSQL·Qdrant)는 공개 서버 묶음(Caddy HTTPS)으로 **클라우드에 미리 띄운 서버**를 쓴다. 두 노트북의 확장은 그 서버 주소(`VITE_API_BASE_URL`)로 빌드한 같은 산출물이다. `localhost` 빌드를 시연 노트북에 설치하지 않는다.
- **노트북 1은 여행을 조사하는 A, 노트북 2는 초대받는 친구 B**다. 서로 다른 Google 계정을 쓴다. 시크릿 창·Edge·Aside·Safari로 대체하지 않는다. 노트북 한 대에 문제가 생기면 남은 노트북의 Chrome 프로필 두 개(A/B)로 바꾸고, 그때부터 "다른 기기"라고 말하지 않는다.
- 팀 기능은 **세션 공유형 1단계**다. 공유는 원본 세션의 라이브 참조이며 이후 그 세션에 추가되는 페이지도 포함된다. 팀원은 읽기 전용이고, 개인 전체 방문 기록이나 공동 편집을 보여주는 기능이 아니다.
- 팀 생성·초대·공유는 사이드패널 `설정` → `팀`과 세션의 `팀에 공유`로 진행한다(새 탭 사용자 메뉴에도 팀 설정이 있지만 대본은 사이드패널로 통일한다). 팀 Ask는 사이드패널 하단 질문 입력창에서 실행한다.
- `화면 확인`은 실제 Chrome 확장에서 클릭 후 기대 결과까지 본 경우만 쓴다. 소스·자동화 테스트·빌드 확인·헤드리스 재생은 별도 근거다. 결선 환경에서 실제 화면을 보지 못한 단계는 모두 **미확인**으로 남긴다.
- 온보딩의 예시 세션·mock 타임라인은 실제 수집 결과로 보여주지 않는다. 사전 결과를 사용할 때는 실제 리허설에서 만들어진 자료인지 확인하고 "사전에 처리한 결과"라고 말한다.

## 2. 시연 전 점검표

이 표는 준비 담당자가 채운다. 현재 체크하지 않은 항목은 통과로 간주하지 않는다.

- [ ] **클라우드 서버:** 공개 서버 묶음으로 띄운 서버의 HTTPS 주소, PostgreSQL·Qdrant 가동, 백업 상태를 확인한다. `GET /health` 200은 고정 응답이라 로그인·세션 조회·검색이 실제로 되는지 따로 본다. 연결 실패를 복구한다며 `docker compose down -v`를 실행하지 않는다.
- [ ] **AI 키:** 서버 환경의 A.X-K2·K-EXAONE(dedicated endpoint)·KT 믿:음·Upstage 키가 살아 있는지 실제 세션 분류와 Ask 한 번으로 확인한다. dedicated endpoint는 켜 두는 동안 과금되므로 켜는 시각을 정해 둔다. 키·환경 파일은 화면에 띄우지 않는다.
- [ ] **빌드 고정:** 서버 주소로 빌드한 확장의 버전·확장 ID·빌드 커밋을 기록하고, 두 노트북에 같은 산출물을 설치한다. 생성 파일은 커밋하지 않는다.
- [ ] **OAuth:** Chrome 확장용 OAuth 클라이언트의 항목 ID가 두 노트북에 설치된 확장 ID와 맞는지, 확장과 서버가 같은 클라이언트를 쓰는지 확인한다. 동의 화면이 테스트 상태면 A/B 모두 테스트 사용자로 등록한다. `extension/wxt.config.ts`는 클라이언트 ID가 없어도 빌드가 통과하므로 빌드 성공을 로그인 준비 완료로 보지 않는다.
- [ ] **두 노트북 로그인:** A(노트북 1)·B(노트북 2)가 각각 별도 Google 계정으로 Chrome과 Orbit에 로그인했다. 계정 주소·아바타·기존 바로가기가 발표 화면에 보이지 않게 시연 전용 계정을 쓴다.
- [ ] **수집 동의:** A는 시연 전용 프로필에서 `탐색 기록 수집`과 `본문 저장`을 켠다. 자동 동기화(주기)는 기본 off지만 10분 유휴·대기 개수 기준 동기화는 따로 돈다. 준비 중 페이지를 다 본 뒤 자리를 비우지 말고 바로 `세션 분류`를 눌러 분류 시점을 맞춘다.
- [ ] **시나리오 데이터:** §3의 S1(제주 여행)·S2(러닝화 쇼핑)를 준비했다. S1의 제목·요약·페이지 목록·탐색 타임라인과 검색 가능 상태를 실제로 확인했다. 개인정보·로그인 URL·다른 작업 탭이 섞이지 않았다.
- [ ] **라이브 팀과 예비 팀:** 이번 회차의 새 팀 이름(예: `제주 여행`)을 정한다. 예비 팀 T0는 A/B가 미리 참여하고 S1 공유·해제까지 검증한다. 본 시연 시작 전 T0에서 S1을 공유 해제한다. 예비 팀 준비가 안 됐으면 장애 때 팀 단계 전체를 생략한다.
- [ ] **초대 코드 전달:** 코드는 영문 대소문자·숫자·기호가 섞인 16자라 소리 내어 불러 입력하지 않는다. A가 복사한 코드를 두 노트북에 미리 열어 둔 시연 전용 메신저 대화(또는 공유 메모)로 보낸다. 실제 코드는 대본·로그에 남기지 않는다.
- [ ] **네트워크:** 두 노트북의 전원·절전·Wi-Fi, 클라우드 서버 접속, Google 로그인, 세션 분류·Ask의 실제 성공을 확인한다. 유선 LAN을 우선하고 휴대폰 핫스팟을 예비로 둔다.
- [ ] **화면 준비:** 외부 모니터(HDMI)에 어느 노트북을 띄울지와 전환 방법을 정한다. A 홈·사이드패널, B 사이드패널·아틀라스 탭을 준비하고 알림을 끈다.
- [ ] **실측:** §5에서 로그인 A/B, 동기화, 개인 Ask, 팀 Ask의 시작·종료를 기록한다. 질문 전송 후 첫 답변 본문까지의 시간과 답변 완료까지의 시간을 나눈다.
- [ ] **3분 드라이런:** §4를 스톱워치로 한 번 완주한다. 시간을 넘기면 §4의 생략 규칙을 적용해 다시 확인한다. 실패·생략한 단계를 성공으로 채우지 않는다.
- [ ] **장애 대비:** 사전 처리한 시연 데이터(처리 시각 기록)와 시연 영상을 준비한다. 사용할 때는 라이브 화면이 아니라는 사실과 기록 시각을 밝힌다.

### 데이터 준비 순서 — 발표 3분에 포함하지 않음

1. A에서 수집 동의와 본문 저장을 확인하고 S1-1 → S1-6을 한 번에 방문한다. 각 페이지를 20~40초 읽고 스크롤한다. 이 체류시간은 재현을 위한 준비값이며 제품의 세션 생성 보장 조건은 아니다.
2. 사이드패널 `타임라인`에서 제목·시각·도메인과 `대기` 배지를 확인하고, 날짜 헤더의 `세션 분류`를 누른다. `세션 분류를 요청했어요` 알림은 요청 전달만 뜻한다.
3. `세션` 목록에 제주 여행 세션이 생기고 요약·페이지가 준비되는지 기다린다. 생성된 제목을 그대로 기록해 S1이라고 부른다. 페이지가 두 세션으로 갈라지면 Atlas의 병합 제안으로 합칠 수 있는지 확인하고, 합친 경우 "자동 생성 뒤 병합했다"고 기록한다.
4. 우도 페이지를 하루 뒤에 따로 보면 기존 세션에 붙지 않고 새 세션이 될 수 있다(재생 결과 재방문 이어 붙이기 0/22). 그래서 S1은 **한 번에 방문한 뒤 한 번 분류**한다. 라이브 참조(V09)는 리허설에서만 확인하고, 실패하면 "공유 뒤 추가 페이지 반영"을 발표에서 빼고 미확인으로 남긴다.
5. S2(S2-1·S2-2)는 S1 분류가 끝난 뒤 따로 방문하고 분류한다. 별도 세션이 만들어졌는지 확인하며, S1에 섞였으면 공유하지 않고 준비를 다시 한다.
6. A 개인 범위에서 Q1·Q2와 S1 근거를 확인한다. B는 팀 참여 후 S1만 보이는지 확인한다. 사전 답변을 쓰려면 해당 질문·범위·실행 시각을 기록한다.
7. 시작 직전에는 S1이 공유되지 않은 상태, A의 범위는 `개인`, B의 Ask는 새 대화 상태로 맞춘다. 실제 사용자 세션을 삭제하거나 DB를 초기화해 상태를 맞추지 않는다.

### 진행자가 지킬 생략 규칙

- 종료 시각은 고정한다. 기다린 시간을 뒤 행에 더하지 않는다. 먼저 Q2-1·아틀라스 세부 탐색·답변 전문 낭독을 생략한다. 실패한 선행 단계가 있으면 그 결과에 의존하는 후속 단계도 생략한다.
- 노트북 전환은 외부 모니터 입력 전환(또는 케이블 이동)으로 한다. 전환에 3초 넘게 걸리면 리허설에서 모니터를 노트북 1에 고정하고 B 화면은 노트북 2를 심사위원 쪽으로 돌려 보여주는 방식으로 바꾼다.
- T0를 쓸 때 "오늘 사용할 팀"은 A/B 양쪽에서 T0로 맞춘다. 새 팀에 공유하고 예비 팀에서 찾는 실수를 피한다. 팀이 없으면 범위 선택기가 보이지 않는 것이 정상이다.
- D06–D08은 생성→발급→참여를 보여주는 기본 대본이다. 사전 참여로 건너뛴 경우 이 세 단계의 라이브 성공을 주장하지 않는다.
- 동기화 요청, 로컬 대기 수 감소, 요약 준비, 검색 가능은 서로 다른 완료 시점이다. 요청 알림이나 로컬 전송 상태만 보고 자동 세션 생성·색인 완료라고 말하지 않는다.
- "모든 화면에서 즉시 사라진다" 대신 "다시 조회해 확인한다"고 말한다. 과거 화면·이미 받은 Ask 답변을 원격으로 회수하는 기능으로 소개하지 않는다.
- API 오류·빈 결과·부분 답변은 그 상태대로 설명한다. 장애 시 준비한 실결과·시연 영상을 쓰려면 현재 라이브 화면이 아니라는 사실과 기록 시각을 밝힌다.

### 심사위원 체험(3분 대본 밖)

- 심사위원이 Ask에 질문을 직접 입력한다. 렌터카 면책금처럼 재생에서 흔들린 질문이 나오면 결과를 그대로 보여주고 근거 카드를 함께 연다.
- 원하면 노트북 1에서 임의의 사이트 2~3곳을 본 뒤 `세션 분류`를 눌러 새 세션이 생기는 과정을 본다. 처리에는 서버 배치 시간이 걸리므로 기다리는 동안 다른 화면을 설명한다.
- 후속 질문·혼동 경고·폴더 자동 배정·열린 탭 이동·팀 수집 모드(`팀 수집 허용` 뒤 시간 정해 켜기)는 체험 시간에 보여준다.

## 5. 결선 환경 전체 검증 절차와 대기시간 기록

### 시간 측정 방법

결선과 같은 클라우드 서버·빌드·시연 데이터·네트워크로 로그인은 A/B 각 1회, 동기화와 각 Ask는 가능하면 3회 측정한다. 반복 결과는 각각 적고 성공한 빠른 회차만 골라 평균을 내지 않는다. 이미 로그인된 상태를 새 로그인처럼 재지 않는다.

- 로그인: `Google 계정으로 계속` 클릭부터 홈과 인증된 세션 조회까지. 계정 선택·동의에 쓴 시간도 포함하고 별도 메모한다.
- 동기화: `세션 분류` 클릭부터 ① 타임라인 분류 배지 ② 세션/요약 표시 ③ Q1로 검색 가능까지 따로 잰다. 로컬 `lastSyncAt`은 전송 시점일 수 있어 최종 완료 기준으로 쓰지 않는다.
- Ask: `질문 보내기`부터 **답변 본문 첫 글자**까지와 **생성 종료 및 근거 표시**까지를 나눠 잰다. 로딩 표시·근거 카드만 나타난 시점은 첫 답변 본문이 아니다. Q1의 세션 찾기 경로는 답변 생성 지연 측정에서 제외한다.
- 사전 측정 관찰 한도: 로그인 60초, 동기화 300초, Ask 60초. 이는 진행자 운영 한도이며 제품 SLA·타임아웃 값이 아니다. 초과하면 `>한도, 미완료`로 적는다. 라이브 대본의 한도는 §4처럼 더 짧다.
- 모델은 실행 화면/비밀 없는 메타데이터로 확인한 식별자만 기록한다. 확인할 수 없으면 `미확인`. 요청 본문·Authorization·초대 코드 원문은 저장하지 않는다.

| 대상·회차 | 시작 시각 | 첫 본문/분류 배지까지 | 완료/요약까지 | 검색 가능/근거 | 결과·모델·메모 |
|---|---|---|---|---|---|
| 로그인 A / B | 미측정 | 해당 없음 | 미측정 | 미확인 | 결선 환경 미구성 |

자동화 테스트와 헤드리스 재생은 이 표의 실제 화면·시간 측정을 대신하지 않는다. 표를 채우기 전에는 "전 단계 시연 검증 완료", "3분 완주", "몇 초 이내 답변"이라고 발표하지 않는다.
